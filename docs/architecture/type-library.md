本轮用户所称的“数据库”指类型库。维护流程管理的是页面能力及其证据；SQLite 观察库、计划版本库与可信执行注册层仍是不同资产。持久化方案和管理界面尚未选定，当前没有脚本数据库、动态插件装载或任意组合数据库。

## 四个角色独立选择与执行

分支可带 `page_types`，四个角色分别填 `{type_id, implementation_version, params}`。绑定可省略，旧 kind／CSS 字段自动解析为精确兼容类型 @1。规范化不改原计划，参数投影到对应结构字段；与已有结构冲突时拒绝。params 只允许该角色结构字段，不接受教师 JSON、来源资格、证明、任意嵌套对象或中文姓名选择器；严格模型和有效参数以 page_types 为准。

| 角色 | 输入／输出 | 实际分派 |
| --- | --- | --- |
| entrance：入口／栏目 | 浏览器上下文与分支 → EntranceCapture(html, source_urls, errors, evidence)，仅准备／发现来源，不采分页 | [harvest_workflow.capture_sources](../../server/harvest_workflow.py) 调用 entrance；公共层对照导航子集合与绑定 |
| pagination：名单分页 | 分支、浏览器与 checkpoint 参数 → (pages, errors, evidence)，pages 保留 URL／HTML | [browser_batch_tool._capture_sources_with_state](../../server/browser_batch_tool.py) 调用 pagination 后保存原件、核验覆盖 |
| roster：名单读取 | CapturedRosterPage、计划／人工姓名决定 → 同步 RosterReconciliation：候选、来源、观察、未解决项 | harvest_workflow.reconcile_rosters 对每页分派所选解析器；不绕过来源与身份门禁 |
| detail：个人详情 | 实际个人 URL、浏览器与正文范围 → ProfileCapture(html, proof, errors, meta) | harvest_workflow.capture_profiles 逐 URL 分派；公共层保留正文证据与来源关联，冲突绑定阻断 |

入口与详情的生产 fallback 已使用显式 DTO。低层接口对旧八类型 @1 保留旧组件形状兼容；新定义不能用 None 加闭包写入代替 ProfileCapture。字段解析、来源审计、身份合并、复核与导出继续由公共链组织。

`kind=roster/navigation/segmented/image_table` 是兼容形态，不等于四角色目录。导航可用旧同构 child_branch（无 URL），或互斥的完整 child_branches；后者每个孩子有自己的 URL、来源、结构与绑定，可递归表达有界异构分支。实际发现 URL 集须与显式集合一致；重复、多配、漏配、跨站与未证明入口保持未解决。当前父导航不支持分页，不凭两个样例证明显式全集。

## 当前可信机制与适用边界

| 类型（均为 @1） | 机制／限制 |
| --- | --- |
| entrance.direct、entrance.navigation | 旧直接来源准备、旧导航链接发现，沿用对应浏览器证明 |
| roster.cards、roster.segmented、roster.image_table | 旧卡片／媒体读取、分段平铺、图片表格；segmented、image_table 与严格空态须各自精确 legacy roster@1 |
| pagination.single_page、pagination.next_control | 旧单页或 next 控件；single_page 仍需真实终止证明 |
| detail.profile | 旧个人页读取与正文范围证明 |
| [roster.rank_grid](../../server/page_type_rank_grid.py) | 按明确职称组、唯一标题起点和名单单元独立解析，单元可多人；每人链接按自身 anchor 归属。未知职称／token／结构及同页同名同主页多位置保留未解决，不调用旧 cards parser 代替 |
| [entrance.scoped_links](../../server/page_stage_types.py) | 当前已加载 navigation DOM 中选定容器的可见同站 descendant anchors；保留完整来源集合，需无未证明父分页，不是任意动态栏目遍历 |
| pagination.verified_next | 普通 roster 的唯一 next 点击链、每页来源与真实变化／末页终止；不支持 initial_click_selector 或同时 single_page，达到上限不能算完成 |
| detail.article_region | 唯一语义 article 正文区域及其可见、稳定、完整范围证明；不覆盖任意布局或 PDF 本人解析 |

三项新 DOM 机制的实现、probe、validator 在 page_stage_types；rank-grid 是独立名单解析器。它们通过注册分派接公共链，不在核心 invoke 按新 ID 添分支。其他 PDF／图片能力继续由现有媒体模块处理，不能写成已全部转换为独立角色类型。

## 选择、实际证明与版本失效

分支侦察先用只读 `page_type_catalog` 查角色／ID／版本与适用、参数、输入／输出／失败合同，再选择实际结构；目录不提供代码／import path。来源资格由 browser_verify_source 独立核验。名单 proof 使用同 ID／版本／有效参数的实际解析器，rank_grid 不能借用旧 cards 证明。

新入口／分页／详情须注册完整 stage_probe、同步 evidence_validator、evidence_contract，并用 `browser_verify_stage` 实际执行所选 handler。工具保存原件与结果 metadata；run_stage_probe、stage_evidence_for_result 校验真实结果，不给旧证据贴标签。精确旧八类型 @1 保留原协议，复制旧定义注册 @2 不继承豁免；目录出现或完整注册仍不免除适用、来源和提交门禁。

阶段证明绑定 role、type_id、implementation_version、effective params、requested_url、final_url、实际 source_html_sha256、implementation_digest 与机制 payload。详情用自身原件，分页保留全部页；不能借名录哈希证明个人正文。超 inline 大小的完整结果以本地文件 SHA manifest 读取校验，缺原件／metadata／完整包或篡改失败关闭。模型只提交结构计划，不手写 confirmed、SHA、stage_evidence 或教师字段。

实现摘要由实际注册 implementation／probe／validator／适用条件／参数模型源码 SHA 与确定性代码字段指纹组成，不用随执行 intern 状态变化的 marshal 编码。registered_implementation_manifest 支持契约缓存与 [source_review](../../server/source_review.py) 决定绑定；selected_implementation_digest 递归选择计划定义，[HarvestState](../../server/harvest_state.py) 为非 legacy 选择隔离恢复 namespace。源码漂移使旧证明／相关复用失效，不是手填相同版本号即可继续用。

## 维护根因分类

在用户已分配的维护任务中，先检查已有类型和组合，再根据实际页面证据归类。下面决定修改位置；从观察、候选到验证和发布的工作顺序见 [类型库维护流程](#类型库维护流程)。

| 情形 | 正确的处理范围 | 必要依据与边界 |
| --- | --- | --- |
| 选错类型 | 修识别或分派 | 页面符合已有类型，实际选择却不符合；不能把分派问题算新类型 |
| 已有类型的合理配置差异 | 调整该类型允许的配置 | 对照适用条件与当前 Schema，依据实际结构核实参数；超出能力边界不能伪装成配置 |
| 合理变体扩展 | 扩展原类型并说明适用边界与版本影响 | 同一识别／读取机制、人员边界和证据规则下的结构变体；若需要另一套交互、解析或证明机制，转为新增类型 |
| 真正缺少类型 | 新增对应结构类型及处理器 | 已有类型及组合确实不能支持，需要不同机制；说明与相邻类型的差异、适用与排除条件，不按院校名称或域名堆例外 |
| 类型内实现缺陷 | 修对应脚本并回归该类型 | 类型选择及输入符合契约，处理行为违背该类型要求；核对该类型正例与反例 |
| 已有能力可组合 | 组合对应角色或异构分支 | 入口、名单、分页、详情分别选择已有类型，核对接口与证据传递；组合差异本身不新增整院类型 |
| 类型职责混杂或重复 | 有证据后拆分、合并或弃用 | 拆分无关机制，合并真正相同的合同；明确替代关系、旧计划影响和历史版本处置，不删除反例或强制改绑旧任务 |
| 跨类型公共流程缺陷 | 有证据后修公共流程 | 如调度错误、同名记录覆盖、简介／邮箱串行、重试丢来源证据、人工决定失效或导出旧数据；沿实际调用者证明影响，不把一个页面不匹配自动扩大为公共重构 |
| 网站故障、权限或访问限制 | 如实记录，按明确访问／重试策略处理 | 保留请求、页面和故障证据；不能新增类型或降低校验伪装成功 |
| 证据不足、来源或选型仍有疑义 | 保留观察／未解决并列所缺材料 | 先补原件、归属或匹配依据；未知不等于缺类型、无师资或成功 |

核心分界：先核实访问、来源、选型与允许的配置，确认问题不能由已有类型及组合解决。页面属于类型已经承诺的范围却处理错误，属于修复；布局变化但读取机制、人员边界与证据规则不变，属于原类型的合理变体扩展；必须采用不同的读取或交互机制且已有组合无法支持时，新增对应类型。扩展须说明仍属同一机制的理由，并以相似反例约束边界。新增正例不能靠删除排除条件、放宽来源／身份／完整性核验来通过。

任何修复都检查既有成功样本影响：比较人员、字段归属、完整简介、来源、覆盖、复核与交付状态。真实能力退化须定位修复；新校验揭露旧数据错误应更正旧结论，不能为验收放宽标准、删失败样本或把人数增加当质量提升。原件不足时报告未验证，不能靠不断追着新学院修复证明正确。

## 类型库维护流程

以下是本轮对齐的维护规范，适用于用户已分配的类型库维护工作。它规定工作记录和验收条件；不是已经实现的数据库状态机或自动准入功能。具体任务、决定和证据沿用对应工单、PR 或已有问题记录，不另建平行待办。

### 一次维护的工作顺序

1. **确定入口与范围。** 从用户任务、实际报错或待核结构案例开始，记录目标页面、相关角色、运行版本和已知影响。相同根因的案例归到同一工作项；是否相同由结构和调用证据判断。完成条件是本次要解决的问题、影响边界和验证材料明确，额外问题另行记录。
2. **保存观察与原件。** 保留 URL、获取时间、页面或附件原件及摘要、结构特征、失败步骤和预期行为；页面变化产生新的证据版本。记录已有案例与类型的关联，保留未读取和归属不明范围。完成条件是问题可由原件或明确步骤复现；单有错误消息或截图时标明证据缺口。
3. **检查已有能力并分类。** 按入口、名单、分页、详情逐角色检查目录、适用条件和已有组合，再按 [维护根因分类](#维护根因分类) 选择配置、选型修复、类型修复、扩展、新增、组合／拆分或公共流程修复。完成条件是能解释已有类型为什么适用或不适用，以及为何在选定位置修改；暂时不匹配不自动证明缺少类型。
4. **形成候选及变更说明。** 明确类型 ID、实现版本、处理器、适用与排除条件、参数及证据合同、样本和依赖。修改已有类型时说明旧承诺、触发缺陷和兼容影响；新增时说明相邻类型为什么不能复用或组合。完成条件是候选的行为和边界可审阅，代码与文档描述相符。
5. **验证实际行为。** 用人工核实的真实正例、相似反例、边界样本和受影响历史案例执行实际处理器与相关生产接线。对名单／详情比较人员集合、字段归属和完整正文；对入口／分页比较来源集合、页面变化、终止和覆盖。适配器直接返回“通过”或期待答案不构成执行验证。完成条件是相应合同逐项有结果，失败和缺材料保留，不能只用条数或测试全绿判断。
6. **发布精确版本。** 验证记录关联候选提交、类型版本、执行环境、样本与期待答案摘要、实际结果及验证范围。提交、CI、合并和环境加载按用户任务与仓库实际规则执行；分别记录离线验证、已合并、已加载和真实运行验证。完成条件是本次发布范围内的检查通过且产物可追溯；发布代码不自动证明跨站泛化或整院采齐。
7. **在采集中选择和复验。** 按当前页面逐角色选择已可用的精确类型版本，核实参数、来源资格和实际阶段证明，再组成采集计划。缓存计划仍按当前原件与实现复验；失败回到对应问题分类。完成条件是本次选择、执行和未解决范围有证据，旧站成功不能替代新站验证。
8. **维护、弃用与替换。** 新问题关联回原类型及版本。弃用记录原因、替代项和受影响计划／任务；停止新计划自动选择该版本，已绑定任务须明确继续条件或迁移方案。已知会产生错误事实的版本停止继续使用。完成条件是调用影响已检查、替代或未支持范围明确，旧样本、失败证据和决定历史仍可追溯。

### 探索批次与阶段验证（按任务指派）

用户指派维护 agent 自主探索类型库时，可从可追溯的高校与学院名录建立抽样框，每批随机抽取 10 个学院。访问师资页面与查看采集结果前固定学院名单，记录名录来源、抽样方法、种子及与历史学院、大学和模板的重叠；抽中后的难采、失败、待核和不可访问项保留，不以结果替换。专项业务验证仍按其任务指定的实际母表取样，各自记录抽样框与结论范围。

探索批次用于发现能力边界和维护问题；经过调试的案例进入历史回归。每批按上述流程处理根因，核验程序称成功的结果，保留未完成范围及耗时、实际模型用量与费用；类型数量增加不作为维护完成条件。日常维护按当前工作项执行，探索批次与阶段验证只在任务指派时启动。

本轮拟交给维护 agent 的阶段目标采用以下验收条件：现有类型状态已盘清，发现的可复现程序／类型问题已处理，受影响历史回归通过；在同一冻结版本上完成连续两批各 10 个学院的未见验证，可核验范围内没有新增类型缺口或确认错漏。验证中发现问题则转入回归，修复后重新抽取未见批次；冻结版本变化后不沿用前一版的连续通过结论。不可访问、待核和未完成项不计成功，没有可核验结果的批次不作为验收依据；阶段结论只覆盖实际证据支持的范围。

### 类型、样本与计划分别维护

- **类型定义**记录角色、稳定 ID、版本、识别依据、适用／排除条件、结构参数、输入／输出／失败合同、处理器和证据协议。ID 按可复用机制命名；院校和 URL 是案例背景，不作为类型专用例外。
- **样本证据**记录案例 ID、原件版本与摘要、独立核实的期待结果、核实范围、实际执行结果及所验证的类型版本。样本去重后保留多个任务关联；旧版原件和修复前反例保留。人员数据与原件按现有受控证据位置保存，工作项给出跨环境可访问位置及摘要。
- **采集计划**记录当前页面与角色的精确类型版本、结构参数、来源和证明。某学院的计划通过复验，只支持该计划在相应材料上的使用，不能把其 CSS 配置直接推广成跨学院类型。

类型或样本记录至少能追溯到所属工作项、变更者／核实者、时间和代码版本。已发布记录保留历史。同一类型同一时间由一个维护 agent 负责改写，其他 agent 提供问题与证据；不同根因仍分别记录，由该负责人协调处理，不因同属一个类型就合并为同一根因。不同类型可以并行维护；发布前核对最新版本、共同依赖及相关变更，避免覆写另一项工作。

### 维护状态与准入

维护记录使用以下含义：**观察**是已保存的结构线索；**候选**是正在定义或实现的能力；**已验证待发布**是指定版本在记录范围内通过验证；**已发布可用**是完成相应发布检查、可供新计划选择的版本；**弃用**是停止新选择并说明旧使用处置的版本。拒绝候选保留原因和证据，出现新证据时重新评估。

这些是维护流程状态，不是现行 `SiteTypeRegistry.status` 的替代解释。`observed/accepted/rejected` 不能批准执行能力，注册成功也不能单独充当样本准入。已有类型未取得本规范要求的完整材料时，记录历史兼容与未验证范围，不追认其已经认证；确认缺陷按上面的维护或停用流程处理。

新候选在准入前用于隔离开发与测试；准入依据必须覆盖其声明的边界，包括容易被误接受的页面以及应当保留未解决的失败情形。样本数量随结构差异决定，不以至少两个不同学院的真实正例作为统一发布门槛。只有一个学院的真实案例时，若适用与排除边界明确、期待结果经独立核实、实际处理器的正例、反例及相关历史回归验证均通过，并完成相应发布检查，允许发布；只声明证据支持的结构能力与验证范围，新页面使用时仍逐页检查适用性。一个学院的成功不能单独证明跨站泛化，更多同站样本也不自动形成独立跨站证据。

### 选择冲突、未知与组合边界

多个类型都匹配时，对照识别依据、排除条件及真实执行证据消除歧义，记录选择理由。仍有冲突则保留选型未解决；修复的是识别／分派或类型边界，不能以注册顺序或“哪个输出人数多”暗选。无匹配先保存观察，再按根因分类判断；访问失败、来源资格不明和原件不完整分别保留。

组合须核对角色间输入输出、来源与本人范围、分页终止、版本和证明传递。已有四角色能够完成时直接组合；不同分支可以选择不同类型。新增角色、超出现有 Schema 的交互或改变业务归属属于额外设计范围，先说明缺口，不把它暗塞进配置或公共 fallback。

### 版本、失效与回退

同一机制的缺陷修复或合理变体扩展保留类型 ID；改变采集行为、适用范围、参数语义或证据协议时发布新的实现版本，说明兼容性。不同识别／读取机制使用新 ID。纯文档或不改变行为的整理说明其影响，不因文件变化就宣称新增能力。

已发布的 ID／版本不原位替换行为。修改处理器或其公共依赖时检查受影响的阶段证明、缓存、断点、人工决定和旧产物；按实际绑定失效与复验，不复制旧证明到新版本。回退也须核实当前页面和业务契约，只在旧版本仍有效时使用；保留新旧记录和失败证据。类型合并或拆分写清替代关系，迁移后才能移除旧执行入口。

### 修复后的影响排查与补采

修复后先根据根因、问题类型版本、共同依赖和触发条件确定影响范围，将其他使用问题版本的历史任务列入影响排查。分别记录确认受影响、确认无影响和仍未知的任务及依据；旧任务未报错本身不证明无影响。

- **确认只影响部分个人页**：补采这些页面，并核对人员关联、字段合并、待核状态和导出结果。
- **名单或分页问题可能造成漏人**：重采相关分支，重新核对名单、分页覆盖与人员观察，并补采遗漏人员的详情。
- **影响范围无法确定**：扩大核验范围，必要时重采整个学院；范围未查清前不能按局部修复宣称整个学院已经恢复。

补采产生新的采集运行，关联原运行、维护工作项及修复后的精确版本，保留旧原件、结果和修复关系。复用未受影响材料或判断时遵守 [CONTEXT 的证据复用条件](../../CONTEXT.md#工作对象与证据) 及上述版本失效规则；确认旧结果有误时保留更正记录，不让旧的完成结论继续代表当前结果。实际补采按已授权任务、批次及预算执行，范围外的受影响历史任务记录待安排。

### 本流程的交付记录

一次维护在原工作项集中给出：问题与根因分类；类型／角色／版本和变更范围；原件、期待结果与实际验证证据；历史案例差分；发布／加载／真实运行状态；剩余未知及下一步。人员与字段正确性、覆盖、人工复核量、耗时及模型费用只报告有证据的范围。按问题形成可审阅改动，避免同一根因逐学院追加类型、重复清单或零散 PR。

## 用户目标与仍待验证的差距

| 用户目标 | 当前已实现 | 待验证或另立任务 |
| --- | --- | --- |
| 适用、输入输出、脚本、失败与版本绑定 | TypeDefinition、四角色合同、目录、结构参数、新机制证明 | 新页面识别准确性、跨站适用、全面样本／生命周期；目录本身不证明会选对 |
| 不同页面／环节可组合替换 | 独立四角色、异构子分支与真实替代处理器 | 当前有界 DOM／兼容结构闭环；更多交互、父导航分页、媒体角色化尚未实现 |
| 回归保护与来源复核 | 注册／执行／侦察／摘要回归文件及来源、人工决定门禁存在 | [历史案例](../site-types/) 原件可达性、人员字段真值与旧成功兼容不能由文件存在证明 |
| 上述维护状态、样本准入与版本发布流程 | 现有注册、阶段证明、观察记录及计划版本可作为依据 | 本基线没有把真实正反例、独立期待答案和验证回执作为全目录统一准入门禁；完整生命周期、管理界面与存储方案尚待实现，不由文档更新宣布完成 |
| 全部官方师资与正确归属 | 公共覆盖、来源、身份、交付门禁继续运行 | 实际模型、新学院、昨晚工单未在本次文档整合验收；未知范围须按 CONTEXT 报告“完整性未验证” |

观察库 accepted/rejected 仍不批准执行能力。没有实现数据库类型管理、任意 CMS 适配或零遗漏保证，也未改变业务交付口径。安装／运维保持原入口，部署和采集按用户明确任务执行。
