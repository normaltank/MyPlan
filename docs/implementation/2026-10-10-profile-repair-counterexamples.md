# 保留正文反例，区分访问失败与正文失败

2026-10-10。实现范围：`server/agent_worker.py`、`server/agent_recon.py` 与独立回归测试。未修改生产工单、重启、付费采集、推送或提交。用户最新 AGENTS.md 与 CONSTITUTION v2 为工作依据。

## 问题与真实证据

土木任务 attempt-3 审计 SHA256 `47ebf3ace14e5e391e2911814abacf67ae3906569181d5787b52b7066020642f`。15个正常详情页缺少旧正文 ID，但共同正文 class 存在。保存的第二轮真实浏览器证据已对15个反例和2个普通样例核实新容器；仍不可访问的错误引用被当作还须证明正文的页面。计划拒绝时 worker 以新门禁错误替换已有反馈；下一轮只验证前两个普通样例即可退回旧 ID。详细只读诊断和结构计数保存在本地 `.planning/review/civil-scope/`，不是已修复版生产验收。

## 行为改变

1. 门禁拒绝只追加受控结构约束，不能清空上轮采集实际发现的 URL 反例；完整原计划不被失败阶段返回的部分已接受分支替换。新候选计划重新核对当前目标和卫生契约后才可用于反馈。异常原文不送回模型。
2. 去掉反馈“前20项”裁剪。所有明确失败URL均进入门禁已有的 `repair_profiles` 约束；JSON去重限制相同错误的重复堆叠，不牺牲末尾人员来源。
3. 保留最近实际采集报告、全部记录/路径/计数和未解决项。后续门禁拒绝追加安全问题，不把完整报告替换成只有门禁状态的小字典。
4. 当前捕获明确记录 `profile_navigation_failed` 或 `fetch_failed[:…]` 时，同URL伴随的正文未核实/缺失只说明拿不到可读页面；不作为给同分支正常页面改CSS的反例。空正文、隐藏正文和选择器缺失如果没有失败获取证据，仍是范围修复约束。

访问失败仍保留在原审计与恢复分类中，候选不删除、字段不伪填，`delivery_ready` 不变成真。本修改不跳过正常的本地访问重试，也不把错误引用认定为“无师资”。

## 门禁证据如何参与

合并后的反例进入 `_run_staged_harness` 的逐分支 `repair_profiles`，同时进入 BrowserScout 运行目标。最终 `selector_evidence_issues` 仍要求本轮具体URL、同选择器/边界、唯一可见容器、稳定DOM、请求结束及完整HTML/正文SHA证明。反馈里写一句“已修复”或只证明两个普通页不能通过；改变了选择器但遗漏第25个已知失败页也不能通过。

本修改不跨会话伪复用旧浏览器证明。原第二轮的真实证明用于定位为何曾有正确容器；后续新会话仍须提供当轮证据。已知范围反例在同一次 worker 修复链内保留，新的实际采集审计负责更新当前事实。进程重启后的长期反例账本不是本提交已实现的功能；既有恢复路径仍逐页重验与审计，不应把入口两样例当完整证明。

## 可复用类型与边界

- **正文包装布局差异**：同名录详情页具有不同ID，不能按前两条链接或URL目录推出全组模板一致；通用CSS必须逐页证明唯一与完整。此次没有学院名称、域名或特定正文class的条件分支。
- **无法读取个人引用**：当前访问失败有独立机器证据，范围失败作为其后果暂不交给结构侦察；原名录、引用和候选继续保留。访问恢复后仍须范围与身份核验。
- **可读取但范围失败**：没有失败获取证据的 missing/empty/hidden 等情况不得归入“无法读取引用”。

这三个边界在共用恢复代码中表达；没有修改侦察计划Schema、模型字段边界或站点模板注册文件。PDF归属和图文邮箱冲突独立处理，本修改不能据此宣称58项错误全部解决。

## 测试与风险

先跑真实 worker → staged harness → `selector_evidence_issues` 红测试，复现15个反例被清空，以及为死链接强迫正常正文扩大范围导致第三轮侦察。修复后两条链转绿。另覆盖25项完整保留、失败阶段空分支不得覆盖完整原计划、完整逐URL浏览器证明允许真实恢复、空正文不能凭空归为访问失败、空格URL编码等价和不合法候选计划不回放。

测试使用独立临时数据库和输出目录，模型SDK与浏览器访问边界为固定事件/捕获fixture；门禁和worker控制流真实执行。该测试范围证明恢复机制，不代替实时官网、实际模型侦察或大学交付验收。相关 worker恢复、分支重用、侦察门禁、结构证据、停止策略回归与 Ruff 结果由本轮执行记录报告；提交后仍须等待对应CI最终通过。

最终本地结果：`test_repair_counterexamples` 6项通过；连同 repair_scope、worker_resume_cache、recon_evidence、recon_optimizations、recon_stages、recon_submission、profile_structure_evidence、recon_gate_stop、agent_worker_delivery 共 **85 passed in 43.09s**。相关集合包含已有的本地真实 Chromium 场景；三处改动文件 Ruff 全通过。最后追加“已核实但未获接受的阶段证明”fixture后，新6项再次通过（1.60秒）。未执行实网学院采集与实际模型调用，未提交故没有对应CI结果。

代价：不再截掉末尾反例，结构反馈可能更长。每URL证明是已有审计要求，应通过消解同URL重复问题而不是丢弃约束控制费用。报告保留旧审计事实时仍会有新增门禁问题，调用者需分别识别采集失败与侦察失败；本提交没有以这两种问题的数量相加推导人数。

## 共享恢复分类与队列分流补齐

冻结 `c882c0f` 独立审查复现了一个尚未贯通的调用者：worker 在结构反馈前过滤同 URL 的访问失败伴随正文问题，但共享 `recovery_policy`、报告的 recovery、失败数据库和 API/UI 仍把伴随正文错误归为 structure。原始审计保留是必要条件，不能用此理由让不同调用者对同一故障给出相反的恢复动作。

访问 helper 已迁至 `recovery_policy`，worker 的局部另行过滤删除。共享分类要求当前捕获有同 URL 的 `profile_navigation_failed` 或 `fetch_failed[:…]` 机器事件，才把已登记的 `profile_content_*` 结构问题视为访问失败的后果。普通空正文、另一 URL／片段／查询参数上的正文问题，以及未知 `profile_content_*` 状态均不会据此降级。空格与浏览器 `%20` 仅按既有 URL 编码对应；不推测重定向或合并不同页面。既有 DOM 不稳定／网络未结束机器原因及分支访问依赖也由同一策略继续处理。

worker 的真实失败出口新增内部 `stats.failure_issues`：只保存已登记机器 status、URL／branch_url 和已登记的浏览器瞬态 reason。教师字段、正文、原错误和原异常后缀不进入该上下文；`fetch_failed:…` 归一为 `fetch_failed`，未知状态归一为 `unknown_failure` 并保持 stop。含凭据或邮箱的 URL 不保存到此路由上下文，缺少安全 URL 时不能据它降低正文问题；原 URL 和详细问题仍在本地审计中保留。

queue 的 `failure_disposition` 使用上述上下文调用共享分类，API 与 UI 继续读取该统一分流。独立或未知 summary code 若未被上下文覆盖，仍追加为无 URL 的恢复约束，不能因精简上下文丢失停止／范围问题。旧工单没有该上下文时沿用原 codes／旧错误文本分流，不能从 summary 的“两种错误同时出现”臆测同 URL；未静默重入队。新增上下文不修改侦察 Schema、原始 unresolved、记录、交付状态或人工无师资口径。

新增定向测试先复现 **6 failed in 2.19s**，补齐后 6项通过，再扩展安全元数据、未知 stop、侦察重试和精确 URL 边界。真实 worker `_process`→结构采集审计→独立临时数据库失败持久化→queue→`app.present_task` 均执行：同 URL 访问后果归 access；独立正常页正文缺陷仍归 structure；未知问题仍归 failed；原审计的 unresolved、保留记录和 `delivery_ready=false` 不变。结构浏览器捕获与模型侦察使用固定 fixture，无实网、付费模型或生产状态变更。新10项连同恢复策略、队列分流、原反例、失败类型登记和来源／人工无师资相关回归共 **40 passed in 9.76s**（仅已有 FastAPI/Starlette弃用警告）。提交、CI、加载及学院验收仍需分别报告，本补齐不声明土木全部58项问题已解决。
