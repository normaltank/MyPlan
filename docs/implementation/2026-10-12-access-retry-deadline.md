# 访问补采耗时与中断前运行报告

对应资源与环境工程学院工单 `ebd2991b7b474f18b2cc10cea22753f4`。排障基线为主线 `eea742a`，原始审计、失败记录及历史结果保留。

## 已观察的问题

最新保存采集耗时 1016.223 秒，其中个人页与范围核验 440.314 秒、媒体读取 345.314 秒。工单最终报 2700 秒超时；常驻 worker 日志显示访问失败后进行了补采。旧编排允许在剩余时间不足时继续完整采集，并且只在访问补采循环结束后写 `runtime-report.json`。因此被截止时间中断时，运行报告可能仍是前一次执行的旧文件，不能据旧报告推断最新阶段耗时。

这些证据证明重复补采和运行报告保存时机的问题，不证明每次重复采集的耗时相等，也不证明官网本身卡死。

## 当前修复

每次采集完成立即保存本轮运行报告。开始同计划访问补采前，用刚完成采集的实测耗时与当前剩余时间比较；不足时保留原报告、记录和未解决项，追加既有 `repair_skipped_task_deadline` 状态，结束本次处理。仍在原 2700 秒边界内运行，不改变重试次数、学院范围、人工决定或交付门禁。

这是对下一轮时长的估计，不保证官网下一次响应同样快。初次采集和正在进行的采集仍可能真正超时。
