## 二、降低侦察消耗

### 对照方法

- 同一时段、同一模型（deepseek-flash，推理强度 high），5 个学院并行。
- 数据库与输出目录相互隔离，比较改动前后两份代码。
- 费用按同一价表估算，不是账单。
- 云端下载不到学校网站的图片，两轮都会反复重试，所以耗时对比不代表真实速度。

| 学院 | 请求（前→后） | 输出 Token | 估算费用 |
| --- | ---: | ---: | ---: |
| 绍兴大学 鲁迅人文学院 | 23 → 25 | 11.2k → 11.6k | $0.021 → $0.022 |
| 绍兴文理学院 教育与心理学院 | 62 → 79 | 16.6k → 22.8k | $0.039 → $0.050 |
| 湖南中医药大学 信息科学与工程学院 | 17 → 14 | 5.6k → 7.5k | $0.013 → $0.016 |
| 山东中医药大学 中医药创新研究院 | 77 → 44 | 47.9k → 33.8k | $0.087 → $0.056 |
| 鲁东大学 土木工程学院 | 139 → 59 | 68.0k → 16.0k | $0.119 → $0.034 |
| 合计 | 318 → 221 | 149k → 92k | $0.278 → $0.179 |

绍兴文理变多，是因为一张卡片上的外籍译名读不出来，被当成结构问题补缺了两轮。这个问题此后已改为走人工确认（见第三节），还没有实网复跑。

### 消耗来源与处理

1. **个人页正文容器反复排查**（鲁东单个分支 14–28 次请求）：
   - 原因：工具只回一句"hidden"，模型就用脚本反复查可见性、滚动、网络。
   - 处理：`browser_verify_profile` 一次打开并核实最多 3 个样例。不带选择器时给出候选容器，以及各样例共同通过的选择器（优先稳定的类名）。失败时附隐藏元素位置和已通过检查的替代容器；网络未静时自动再看一次。
   - 效果：鲁东每个分支降到 5–6 次。
2. **页面预览丢字**：
   - 原因：预览没展示出来的文字也被记成"已看过"，再次打开时拿到空文字，模型只好写脚本读正文。
   - 处理：只记录实际展示过的行。入口发现另外给出每页的人名链接数、顿号名单人数、邮箱数、图片数（只有计数）。
   - 效果：山东中医药入口发现 51 → 20 次。
3. **补缺浪费**：
   - 只要问题都落在已采用的分支上，补缺就沿用上一轮的入口发现。
   - 出问题的分支带着问题单独侦察，不再照搬同模板兄弟分支的选择器。
   - 补缺后计划与上一轮完全相同，就不再重复采集。
   - 个人页、翻页后第 2、3 页上的问题，归到它所在的分支。
4. **推理强度**：可按入口发现、分支核实两个阶段分别设置（`DSH_EFFORT_DISCOVERY`、`DSH_EFFORT_BRANCH`），尚未做对照实验。

## 三、准确性核对

### 字段提取修正

- **邮箱按位置归属**：出现在本人名录卡片、个人页正文容器或本人简历图里，就是本人的，不看域名和前缀。
  - 同一邮箱出现在多位教师的页面上：算公共邮箱，不归任何人。
  - 邮箱只拼出了某位同事的姓名：归那位同事。
  - 一人有多个邮箱：拼出本人姓名的优先，其次按页面顺序。
- **姓名**：
  - 去掉"博士"等学位后缀。
  - 各卡片都重复的链接文字（如"查看详情"）按模板处理，改用卡片自己的姓名，支持多段外籍译名。
  - 已核实卡片上仍读不出的名字进"姓名待确认"人工复核，不再交给模型补缺。

### 核对与抽检（只提示，不拦交付）

- **字段核对**（`server/field_checks.py`）：
  - 姓名、邮箱是否出现在来源页。
  - 邮箱是否被多条记录共用。
  - 职称是否在规范词表内。
  - 简介写的是不是别人。
- **人数核对**（`server/headcount_check.py`）：
  - 导航普查：不用模型，打开学院站点的菜单页，用确定性读取找出列有人名的页面，列出没入库的姓名和来源页标题。
  - 翻页器上的"共 N 条"与实际采到的卡片数对照。
  - 学院介绍里的"专任教师 N 人"与入库人数对照。
  - 结果写进审计和任务统计，网页结果行显示摘要。
- **试跑时报出的差额**（都附来源页标题，方便人确认）：
  - 鲁东：行政人员 11 人（按规定不采）。
  - 绍兴大学：曾执教教师 28 人。
  - 湖南中医药：学院介绍写专任教师 67 人，入库 73 人，需要人看。
- **人工抽检**（`python -m server.spot_check`）：
  - 随机抽样（有邮箱、无邮箱各半），附原页片段，生成核对页。
  - 同时生成复核结论模板，字段与 `server/harvest_benchmark.py` 一致，积累起来就是准确率基准。
  - 抽 n 条全部正确时，错误率在 95% 把握下约不超过 3/n。

### 关于"两套方案对比差额"

两套方案必须在不同的地方出错，对比才有意义。所以第二套方案用的是不调用模型的导航普查，而不是让模型再侦察一遍：同一模型再跑一遍，容易在同一处出错，Token 还要翻倍。模型两次独立侦察的对比适合做抽检，本次 5 个学院的前后两轮就是这样比出了 1 条差额。

## 四、师资链接输入

- **格式**：每行 `大学 学院 学院主页 [师资链接]`，可直接粘贴表格。同一学院的多行合并成一张工单（`server/intake.py`）。只填三列的学院，照旧由系统自己找名录。
- **入队前校验**：
  - 列数、网址无效或同一学院主页前后不一致：逐行报错。
  - 可疑行需确认后才入队：链接不在学院站点或目录下、学院主页与同校多数学院不在同一域名。同事给的湖南科技学院样例里，"传媒学院"的主页在 `hnist.cn`，同校其他学院都在 `huse.edu.cn`，会被标出来。
- **侦察**：
  - 入口发现阶段只核对给定链接（`server/recon_provided_links.md`）。
  - 队伍概况页、行政与教辅名单、曾执教名单、失效或跨校链接不采；目录页换成下面的子名单页；给定链接都不是名录时，才从学院主页找。
  - 这类工单不使用、也不写入按学院主页缓存的计划。
  - 人数核对会同时读取全部给定链接，列出"采用 / 未采用"的链接和页面标题。
- **湖南科技学院 3 个学院试跑观察**：
  - 入口发现：给链接比只给主页少 0–4 次请求（5 比 5、8 比 9、9 比 13），两种方式选出的名录完全相同。
  - 概况页（dwgk1、szdwjj）和教辅人员页（jfry）都按规定排除了。
  - 这所学校导航清楚，所以省得不多；导航复杂的学院（如山东中医药，入口发现曾达 51 次）才能省下这一整段。
  - 信息工程学院给的 4 个链接都是概况或风采页，官网可能没有完整名录。这种情况要靠人数核对和人工确认，链接本身解决不了。
  - 该站点从云端访问每页约 9 秒，个人页常常网络不静，而本轮又并发过高导致侦察超时。这组试跑只用来观察流程，不作为耗时或费用结论。

## 五、配置与使用

- `DSH_EFFORT`、`DSH_EFFORT_DISCOVERY`、`DSH_EFFORT_BRANCH`：推理强度（off / low / high / max）。
- `HARVEST_CROSS_CHECK=0`：关闭导航普查（字段核对仍做）。普查最多约 240 秒，受任务截止时间约束。
- `python -m server.spot_check <学院 audit.json> [--sample 30] [--seed N]`：生成抽检核对页。
- 批量输入格式与提示规则见 [运维手册](../operations.md)。

## 七、已知限制与后续建议

1. **慢站点**：个人页核实要求"网络已静"，在慢站点上会反复失败、多花请求。可以考虑侦察阶段放宽这一条（采集阶段仍逐页核实），需要单独决定。
2. **普查的局限**：普查会碰到行政、退休、学生名单，学院介绍里的人数也可能过时，所以差额只能交给人判断。误报多少，要积累实际数据后再决定是否拦交付。
3. **推理强度未测**：分阶段推理强度（例如分支阶段用 low）还没做对照，建议在本机用同一组学院对比。
4. **计划缓存**：给定链接的工单暂不缓存计划，重复采集同一学院时仍要重新侦察。
5. **本机实测**：云端的耗时受图片下载拦截和机器配置影响，建议在本机用同一组学院重跑一次。
