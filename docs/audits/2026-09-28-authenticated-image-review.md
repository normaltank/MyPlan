# 已登录图片复核与多人流程验收

## 完成内容

- 主网页按工单归属提供低置信图片 OCR 行与邮箱冲突复核，员工仅能操作自己的工单，管理员能操作全部。工单审计只从该工单输出目录解析，浏览器不能提交文件路径；复核决定仍绑定原图摘要、OCR 行或邮箱候选集合。
- 全部可复核项保存后，同一失败工单可以重新入队，保持原提交人。worker 将复核决定带入重新采集的每轮尝试；其它身份、分支和覆盖问题仍受原交付门禁约束。
- 管理员网页列出 `scratch` 中无员工归属的历史图片验收材料，并区分待复核与已复核。原 `8765` 本机服务已关闭，原始审计和复核文件未删除。2021 年导师介绍的已复核验收文件仍不是当前专任教师正式交付。

## 验证

- 固定环境正式 `tests/` 回归：**440 passed、1 skipped**。其后补充历史已复核归档、重试后最新审计选择和主网页邮箱复核权限检查；6 项 API 专项与 1 项真实浏览器专项测试通过。
- 隔离数据库的真实 Chromium 三会话验收：管理员通过网页创建两位员工；两位员工分别在网页提单，并核验历史、进度、复核、重新入队、下载和每日统计。互相直接访问对方工单、复核页与大学版本链接均被拒绝，管理员能查看两者。该验收用虚拟记录模拟完成后的交付，不访问官网、不调用 DeepSeek，也不写入正式 `tasks.db`。
- 正式库验后仍为 1 个管理员、112 条历史工单、0 条待处理/运行工单；worker 在线。本机主网页 200，匿名历史与历史复核入口均为 401。旧 `8765` 端口已关闭；`scratch/image-bio-acceptance-rerun` 的 OCR 与邮箱复核决定文件仍在，管理员归档可找到该已完成审计。

## 尚未覆盖

本轮没有在真实图片简历官网上通过新 Web 入口重新发起付费采集，也没有进行 Linux/HTTPS 部署。完整采集效果仍须以独立真实站点验收判断。直接从项目根目录运行 `pytest -q` 会误收集 `scratch` 和根目录的旧实验脚本；正式回归命令指定 `tests/`。
