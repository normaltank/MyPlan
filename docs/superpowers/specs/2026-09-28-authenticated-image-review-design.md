# 已登录工单图片复核设计

## 目标与边界

将未来工单的低置信 OCR 行和多邮箱选择放进主 Web。员工仅能复核自己提交的工单；管理员能复核全部。已有 `scratch` 下的单份验收材料没有工单归属，不能自动算作任何员工的任务，保留为管理员历史材料。服务器部署不在本轮范围。

## 方案

每个工单的审计文件只从 `server/outputs/tasks/<task_id>/attempt-*` 中查找，且必须是该工单目录下的实际审计文件。审计文件和原图仅由服务器读取，不接受浏览器提供文件路径。复核页使用主 Web 的登录会话和 CSRF 校验；所有详情、复核提交和重试先通过相同的工单归属检查。网页在有图片复核事项的工单上显示入口。

原始 OCR 和原图不改写。复核决定仍以原图摘要、OCR 行摘要或邮箱候选集合为依据保存。保存完所有可复核事项后，页面可要求同一工单重试；只允许曾因图片复核事项失败的工单重试，保留原归属与审计历史。重试时从已核实的结构计划恢复，并把复核决定带到实际读取它的采集目录。若结构或其它审计问题仍在，工单继续按原门禁阻断交付。

独立的 `8765` 旧复核服务在这轮不作为正式员工入口；既有用户复核结果保持原样。其历史材料由管理员在主网页查看，不推断员工归属。

## 验收

在隔离数据库和真实 HTTP 服务中建立管理员与两个员工账号，分别提交不同学院。检查各自的工单、历史、复核页、直接访问别人链接、大学版本下载和每日统计；管理员能看到两边。用保留的图片审计夹具检查复核决定保存、证据绑定、同工单重试与再次审计。全过程不得把测试记录写入正式 `tasks.db`，也不调用 DeepSeek。
