# MyPlan：维护改动清理与后续验证计划

本文负责维护改动清理的专项范围和后续专项验证方法。业务目标与类型定义见 [CONTEXT](../CONTEXT.md)，维护根因分类、类型库维护流程与架构现状见 [类型库](architecture/type-library.md)，调用链见 [采集流程](architecture/college-harvest-workflow.md)。用户最新任务确定本轮范围；阅读本文不启动清理、修复、回滚或采集。

## 维护改动清理专项（按用户指派执行）

范围不是最近一个失败学院或最后几个 PR。相关审计要先确认本轮持续维护的开始时间／提交，然后完整梳理该范围内的 **已合并 PR、未合并分支和本地未提交改动**。起点未确定或材料未取得时明确列未知／阻塞，不能把云端干净工作区当作用户本地没有改动的证据。

清理的交付顺序：

1. 固定时间范围、基线提交、分支／PR 头和材料来源；保留他人改动与并发差异。
2. 为每项改动列出实际生产调用链、目标契约、触发样本及影响范围。区分结构能力、配置差异、公共流程、实验与死路径，不按 PR 数量或文件长度判定。
3. 有证据支持地建议保留、撤回或隔离，说明原因、相关依赖及可能受影响的已有成功样本；证据不足者保留未知。不得预设所有维护 PR 都错误，也不得预设某个旧版本可靠。
4. 提出可追溯的恢复基线候选及差分、质量约束和验证材料；缺样本／原件／本地改动就列缺口，不把提议写成已回滚、已恢复或已验收。执行恢复或后续修复由另一个明确任务安排。

完成标准是范围完整、每项判断有依据、材料缺口公开、恢复基线建议可审阅；PR 数量、代码量和运行时长均不是标准。新增功能、架构扩张与额外修复另立任务，到本任务验收点停止，不以不断加代码代替判断。

## 后续专项验证方法（待另行安排）

以下方法保留随机探索、整批证据、历史保护和未见验证的有效约束。只有对应任务明确安排运行范围和预算后才执行；阅读本文不启动采集、扩大当前任务或要求文档整理执行全套测试。

## 1. 全链路代码审查的完成条件

从生产入口追踪调用、数据结构和状态迁移，不局限于最近报错函数：

| 边界 | 核对内容 |
| --- | --- |
| 输入 → 发现 → 计划 | 三／四列契约、给定链接、师资范围、来源角色、分支与分页信息传递 |
| 执行 → 字段 → 身份 | 页面与原件取得、正文范围、媒体读取、字段归属、去重及学院关联 |
| 队列 → 复核 → 恢复 | 失败分类、租约与重试、证据保留、决定绑定与失效、补充材料的入口 |
| 审计 → 汇总 → 下载 | 未知范围、部分与完整交付、工作簿、历史版本及当前任务状态一致性 |

每项发现附文件／函数、实际调用方、反例、影响与验证方式，区分确认缺陷、待验证风险和可维护性问题。审查重复规则、职责交叉、隐式依赖、死分支及修改影响；不能只凭文件长度或测试数量判定代码质量。报告已覆盖与未覆盖范围。

## 2. 抽样协议：先留名单，再看结果

从用户**实际待处理母表**建立抽样框，不用旧失败列表或任意网上学院代替。

抽样记录至少包含母表来源与版本／文件摘要、待处理状态的取值及筛选时间、稳定学院 ID、合并重复行规则、原始行数、有效学院数、排除项及理由、稳定排序、随机种子和抽样方法、选中名单、批次用途。

保留三类材料：

| 样本组 | 规则 |
| --- | --- |
| 历史回归 | 同时保留成功与失败、修复前后及同学院不同证据版本；以显式案例 ID 和原件摘要定位 |
| 随机探索 | 随机覆盖真实业务分布，抽中后不以难采、无师资或输入错误为由替换；状态单列 |
| 未见验证 | 未参与本版调试；在查看结果前固定选择规则和判定方法，冻结版本后运行 |

样本规模按核验能力与运行预算决定，不把某个固定小样本数当成质量门槛。图片、PDF、复杂分页等难类型可单独补充并单独统计。记录大学与模板相关性，披露未见验证集与调试／回归集在大学、模板上的重叠，说明同站新学院、同模板新站和新模板的差别；同一站点的多个学院不是多次独立跨站验证。

若未见样本的结果被用于修改程序，该样本转为调试／回归材料，下一次独立验证使用新批次。抽中但不可访问、人工确认无师资、输入有误和未运行项全部保留。

## 3. 运行记录与整批证据

通过现有采集环境提交已固定批次，先核对加载版本、任务队列与执行范围，避免混入旧工单重排。每个抽中学院都关联批次 ID、输入行和状态；已提交项记录真实 task ID，尚未提交项标明未产生 task ID 并记录原因。

每轮保留：

- 输入与抽样记录；代码提交、实际运行版本、配置、模型与提示词版本、时间和缓存／模板复用条件。
- 发现结果、结构计划、分页及访问证据、页面／图片／PDF 原件与摘要、失败及未读资源。
- 审计、原始观察、交付表与版本、人工问题及决定、独立参考答案、修复前后差分。
- 耗时、实际模型用量／费用证据及人工核验量。

材料按现有证据保存方式存放，工作项记录可访问位置和版本。不能只留下某个 agent 机器上的临时路径。原件不在 Git 中时保留受控位置和摘要，不把完整人员数据随意提交到源码库。

## 4. 核验、共性修复与历史保护

用户或同事对照官网独立确认入口、分支、分页和人员集合，再核对字段、完整简介及身份关系。探索批次和验证批次都检查程序称成功的学院；只抽看已经导出的行无法发现整条漏人或遗漏分支。

按共性原因修复，并运行受影响模块的自动测试、完整必需 CI 和明确列出的历史案例。历史保护至少比较人员集合、字段来源和值、完整简介、学院关联、未解决项及缺失范围；人数不变不能说明没有错人，邮箱人数不变不能说明归属正确。

现有 [case_replay.py](../server/case_replay.py) 和 [spot_check.py](../server/spot_check.py) 是工具入口，必须核实其资源完整性、版本选择、缓存行为和比较粒度。工具缺少检查时记录缺口，不能用其 `ready` 列替代验收。保存页回放与实时官网／实际模型侦察分别报告。

## 5. 冻结与泛化判断

固定待验收提交、依赖、运行配置、模型、提示词及缓存策略后，运行未参与该版调试的新批次。冷启动与复用方案的表现分别说明。每个抽中学院都有结果、失败原因或未运行原因，不进行事后换样。

报告至少包括：

| 指标 | 分母及证据边界 |
| --- | --- |
| 原始流程通过率 | 程序称自动通过数／已提交的抽中学院数，另列未提交与未运行项；只描述流程 |
| 核验后有效范围表现 | 完整正确完成数／人工确认输入有效且应有师资的学院数；有效学院的访问失败仍计入分母 |
| 人员与字段质量 | 正确人员／所有输出人员；另列错填、漏填、官网未提供、待核记录和分支缺口 |
| 查全表现 | 仅在完整名单真值确认时计算召回；资格未知、名单未知和暂不可访问范围单列 |
| 使用代价 | 耗时、模型用量／费用和人工复核量；大量转人工不等于自动能力提高 |

排除项须逐项说明，人工无师资单列。某轮可交付有证据的部分结果，不能因此称全院／全校完整。是否达到常规业务可用，需要这些证据支持，不由测试全绿或修好少数旧案例直接推出。
